# ISO/IEC 30107 alignment

PS04 Deliverable 1, bullet 16, and mandatory task 3 ("evaluate the implementation against applicable ISO/IEC 30107
requirements"). This page states which terms and methods of ISO/IEC 30107-1:2023 and 30107-3:2023 the project
uses, what has been measured, and what is not claimed.

The standards were read through their public previews (definitions, table of contents, introduction). Annex C of
30107-3 ("roles in PAD testing") was not read; the role rules in `docs/eval/protocol.md` are team rules informed by
its title.

## 1. Terms as used in this project

| ISO/IEC 30107 term | Meaning | In this project |
|---|---|---|
| Presentation attack (PA) | Presentation to the capture subsystem with the goal of interfering with the biometric system | Photo, screen, replay, mask shown to the camera |
| PAD | Presentation attack detection: automated determination of a presentation attack | The whole liveness engine: passive texture PAD, frame integrity, planarity, challenges, capture binding |
| PAI / PAIS | Presentation attack instrument (one artefact) / PAI species (one recipe) | Species P1-P8 in `docs/eval/protocol.md`; synthetic species SYN-A1..A9 in the automated suite |
| Bona fide presentation | Normal interaction without attack intent | Live subjects S1-S3 in the automated suite |
| Liveness detection | Measurement of life signs; a subset of PAD | Active challenges are "voluntary reactions" in 30107-1 terms; passive texture PAD is not life detection |
| APCER | Proportion of attack presentations of one species wrongly classified as bona fide | Reported per species and as APCER_max; never averaged |
| BPCER | Proportion of bona fide presentations wrongly classified as attacks | Reported overall and per condition |
| APNRR / BPNRR | Attack / bona fide presentations with no response | Sessions ending `QUALITY`, `DEVICE`, `ENGINE` or cancelled; reported next to, never inside, APCER / BPCER |
| IAPAR | Impostor attack presentation accept rate in a full-system verification test | Planned for operator login (evaluation type c); not measured yet |
| Attack potential | Effort, time, equipment and expertise needed | "Basic": at most 8 hours, USD 30, commodity equipment, 30-minute briefing |

## 2. What is evaluated and how

| 30107 item | How it is met | Status |
|---|---|---|
| PAD mechanism types | Passive (texture model + integrity + planarity) and active (challenge-response) | Implemented |
| Test approach written before testing | `docs/eval/protocol.md` (item under test, units of counting, species, splits, roles, freeze rule) | Written |
| Unit of counting | (a) per attempt, (b) per transaction up to `max_retries`, (c) full-system verification | (a) and (b) measured on the automated suite |
| Classification of one attempt | PASS = accept; counted failures (`PAD`, `INTEGRITY`, `ACTIVE`, `TIMEOUT`, `BELOW_THRESHOLD`, `BINDING`) = reject; other endings = no response | Implemented in `tools/eval/scenario-runner` (`Outcome`) and `tools/eval/analyze.py` |
| APCER per species, APCER_max, BPCER, APNRR, BPNRR | `analyze.py` with Clopper-Pearson 95% intervals | Measured on the automated suite |
| Efficiency (PAD and full-system processing time) | Per-frame and per-decision times in every run | Measured ([engine.md](engine.md), section 10) |
| Enrolment vs verification scenarios | Resident capture (`registration`) vs operator / supervisor authentication workflows, with separate thresholds | Both exercised in the end-to-end runs |
| PAD offline | All evaluation runs and both clients work without a server | Measured (desktop D10, Android A13) |
| Tester independent of the tuner | Team rule in the protocol | Applies to the live evaluation |

people from openly licensed clips, 25 synthetic attack packs, 640x480 at 15 fps). Replaying frames into the engine is
itself an injection path, so these are **technology regression results, not an ISO/IEC 30107-3 evaluation**.

| Configuration | APCER_max per attempt (species) | Pooled APCER per attempt | BPCER per attempt |
|---|---|---|---|
| Shipped (`PASSIVE_THEN_ACTIVE`, registration threshold 80) | **100% (8/8)**, SYN-A3 rigid-motion print and SYN-A8 looped clip | 17.6% (32/182) | 58.2% (39/67) |
| Strict (`policy.registration=ALWAYS_ACTIVE`) | **25% (4/16)**, SYN-A7 adaptive screen replay | 3.5% (8/230) | 68.0% (51/75) |
| Proposed P1-P3 (`ALWAYS_ACTIVE` for registration, login and onboarding; `passive.min_frames=30`; engine sharpness 40) | **25% (4/16)**, SYN-A7 | 1.7% (4/238) | 66.7% (48/72) |
| **Shipped since 2026-09-30** (P1-P3 as defaults, plus engine fixes E1 and E3) | **25% (4/16)**, SYN-A7 | **1.7% (4/238)** | **29.4% (15/51)** |

the engine and defaults in this repository now. Source: `docs/eval/calibration-notes.md` section 0,
`docs/eval/results/20260930/` (before) and `docs/eval/results/20260930-engine-fixes/` (after).

Re-run of 2026-10-05 at the current defaults (bundle 1.3.0, loop window 300 frames, dim-light ending, `ALWAYS_ACTIVE` for all six workflows except `exception_photo`; 275 transactions, counted per transaction and on the first attempt, per species and workflow; [../eval/results/20261005-shipped/README.md](../eval/results/20261005-shipped/README.md)):

| APCER, `registration`, SYN-A7 (adaptive screen replay) | 50.0% (4/8), in both columns; `atk-s3-adaptive-screen` accepted in 4 of 4 seeds, `atk-s2-adaptive-screen` rejected in 4 of 4; source artefacts accepted 1 of 2. **After the screen-pattern check (evening run `20261005b-shipped`): 0.0% (0/8)** |
| BPCER, `registration` | 14.3% (4/28) per transaction and on the first attempt, all 4 from the dim clip `bf-s3-dim`. **After the exposure correction: 0.0% (0/28)**; `bf-s3-dim` passes on the first attempt |
| BPCER, `login_auth` | 0.0% (0/12) |
| Pooled attack APCER (secondary), `registration` | 4.9% (4/82) per transaction, 1.7% (4/238) per attempt |

The intervals in the report treat transactions as independent, which they are not (replays of one artefact repeat the
same frames), so read the counts first. Challenge-response does not stop an adaptive screen replay, and planarity does
not either: the homography check has no attack evidence yet and a screen replaying a real head turn is not shown to
be separable from a 3-D head. Since the evening of 2026-10-05 the passive PAD also looks for a screen's pixel grid and
moire in the face's frequency spectrum ([engine.md](engine.md) section 4); it refuses the synthetic adaptive replay
in 4 of 4 seeds with no change to any bona fide score, but its screens are software-made, so whether it stops a real
screen is open until the volunteer test. Results before and after:
[../eval/results/20261005b-shipped/README.md](../eval/results/20261005b-shipped/README.md).

How to read them:
- The legacy passive-first policy accepts passively any artefact that MiniFASNet scores above 80, which is the known weakness of
  open passive PAD. With challenges on every capture, only an adaptive replay that plays the matching clip for each
  prompt still passed (1 in 4 attempts in the 2026-09-30 data), until the screen-pattern check of 2026-10-05.
- Before the engine fixes, BPCER was dominated by one engine defect (genuine left head turns read as smiles, fixed
  by E1: `TURN_LEFT` now completes 15/15) and one synthetic dim-light pack. Now 12 of the 15 rejected bona fide
  attempts, and all 4 rejected bona fide transactions, come from that very dim pack (`bf-s3-dim`, passive score 3).
- With 8-36 attempts per species the 95% intervals are wide (0/12 has a one-sided upper bound of 22%), so no figure
  here is a security claim.

## 4. What is not yet done

- The live in-house evaluation with volunteers and physical artefacts (species P1-P8, protocol sections 5-8) has not
  been run. Its thresholds must be frozen on the development split first.
- The full-system impostor test (IAPAR at operator login) has not been run.
- IAPAR and FRR (error rates of the full system with face matching) are not computed in the 2026-10-05 run: no record carries a match result.
- Android per-species figures come only from the end-to-end run (for example a printed photo passing passively in
  run 8), not from the suite.

## 5. What is not claimed

- No claim of compliance with, or certification against, ISO/IEC 30107-3, iBeta, FIDO or any "Level 1 / Level 2"
  scheme. Reports use the title "In-house PAD evaluation following ISO/IEC 30107-3:2023 methodology".
- Injection attacks (virtual cameras, emulators, stream substitution, replay into the device API) are outside
  30107 (30107-1 clause 4.1); they are handled by design ([security-privacy.md](security-privacy.md)) and not
  reported as PAD results.
- 3-D masks, make-up and deepfakes are out of scope of the attack potential tested.
- The models' training data are not controlled by the project (MiniFASNet: undisclosed; SFace: research datasets
  in its paper); see `models/SOURCES.md`.

## 6. How the design supports a later certified evaluation

- A certified vendor PAD engine can replace the default behind `LivenessEngineProvider` without client changes
  ([engine-interface.md](engine-interface.md)).
- Every attempt is traceable: engine ID and version, model SHA-256 prefixes, session ID and method are in the
  packet; the evaluation runner records the model-set hash and a configuration hash per attempt.
- The device API already carries a device PAD result when a device advertises `padCapability` (MOSIP issue #1117,
  provisional shape), so a device with its own certified PAD can contribute its decision.
